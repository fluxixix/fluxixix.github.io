# 笔记是写给未来的自己的

大多数人记笔记的失败方式不是「没记」，而是**记了但再也没打开过**。前者只是没有素材，后者是白花时间还制造了「我在学习」的错觉。

问题的根源在于目标定错了：记笔记的目标不是「记下来」，而是「几个月后还能看懂、还能找到」。用这个目标回头看，很多习惯就得改。

## 原则一：写结论，不要抄原文

原文在书里、在文档里、在网页上，抄一遍既不会加深理解，也不会让你更容易找到。

值得写下来的只有两类东西：**你的结论**，和**你还没想通的那个点**。前者以后能直接复用，后者是你的待办。

如果读完一篇文章写不出任何结论，那通常说明还没读懂，而不是「这篇文章没价值」。

## 原则二：带上上下文

笔记里最没用的形式是孤零零的一句结论，比如「用 pnpm 而不是 npm」。三个月后你看到这句话，第一反应是「为什么」。

所以每条结论都要带上**它解决的是什么问题**。写成「依赖装到全局会互相污染，pnpm 的软链接结构能避免 → 所以用 pnpm」，这条笔记就自洽了，不需要回到原文。

上下文里还应该包括时间。技术类结论的有效期通常是有限的，标上日期，将来你才知道它有没有过期。

## 原则三：用自己的话

用自己的话写，会强迫你处理掉所有没真正理解的连接词。用别人的话写，那些「因此」「所以」可以原样搬过来，读起来通顺，但其实什么都没经过你的脑子。

一个很有效的检验方式：**把笔记讲给别人听（哪怕只是假装）**。讲不下去的地方，就是没懂的地方。

## 检索比收集重要

一条找不到的笔记等于不存在。所以结构不用精致，但入口必须明确：

- 按主题分目录，不按来源分（「按书分」会让你找不到，因为你不会记得原话出自哪本书）
- 标题写成一句结论，而不是一个名词。`用 pnpm 避免依赖污染` 比 `包管理器` 好搜
- 允许重复。同一个点出现在两个主题下，就复制两份。为消除重复而设计的结构，最后都会让你在写笔记时停下来思考分类——这是最贵的中断

## 笔记也会腐烂

技术笔记的腐烂速度比想象中快。半年前的版本号、两年前的 API 用法，不标注就会误导自己。

所以清理要定期做，而不是等它烂完。一个月翻一次，删掉不再成立的、合并重复的、把过期的标上日期。删掉不可惜——**留下来的旧笔记比没有笔记更危险**，因为你会相信它。

## 小结

三条原则其实是一件事：**把笔记当成写给陌生人的说明书**。那个陌生人就是几个月后的自己，他不记得你的思考过程，不知道当时的背景，也没耐心猜。写的时候多问一句「他能看懂吗」，笔记的质量就上去了。
